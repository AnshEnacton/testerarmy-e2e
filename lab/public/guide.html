A practice app for the e2e runner

Learn it by running it.

Harbor Desk is a tiny clinic front desk. The tests in lab/tests drive it. This page is the map: what to run, what each test is proving, and where that same check shows up on a real product.

Start here

Open a terminal in this project. You can leave this page open beside it.

  1. Look at the app yourself.
    npm run lab
    Then open http://127.0.0.1:4317. Sign in with qa@clinic.test / clinic-pass. Click through Board, Patients, Intake, and Settings. Stop the server later with Ctrl+C. You do not have to stop it to run tests: the tests start their own copy on a free port.
  2. See the test list without running anything.
    npx e2e list --config e2e.lab.config.ts
  3. Run the exact tests. These do not call a model.
    npm run test:lab
  4. Watch one file in a real browser window.
    npx e2e run --config e2e.lab.config.ts lab/tests/board.e2e.ts --headed
Your other config is untouched. npx e2e run and npm run test:e2e still use e2e.config.ts and tests/example.e2e.ts. The lab only runs when you pass --config e2e.lab.config.ts, which the test:lab scripts already do.

Shape of a test

A test file is a small script. test from @e2e-dev/web gives you a browser. expect from e2e checks the screen. The runner starts the app, opens a fresh browser for each test, and closes it after.

import { test } from '@e2e-dev/web';
import { expect } from 'e2e';

test('signs in with the practice account', async ({ app, screen, browser }) => {
  await app.open('/login');
  await screen.getByLabel('Email').fill('qa@clinic.test');
  await screen.getByLabel('Password').fill('clinic-pass');
  await screen.getByRole('button', 'Sign in').tap();
  await expect(browser).toHaveURL('/board');
  await expect(screen.getByRole('heading', "Today's board")).toBeVisible();
});

Three fixtures do almost all of the work:

NameYou use it to
appOpen a path: app.open('/patients'). Also go back, clear storage, or take a screenshot.
screenFind a control and act on it: tap, fill, check, select, hover, press a key.
browserThings only a browser has: the URL, viewport size, downloads, network stubs, native confirm dialogs, iframes.
agentHand one goal to a model, in plain language. Covered below. Needs an API key.
On a real app. Open the page, do the thing a user does, then pin the fact that must stay true. A heading, a count, a URL, an error. If that fact changes, the test fails and you have a regression.

Exact steps and the agent

You have two ways to drive the screen. Most of this lab uses the first. Two tests use the second.

Exact steps: screen

You name the control and the action. The test does that and nothing else. Use this when the value matters: a price, a count, a permission, an error message, a file name.

await screen.getByLabel('New task').fill('Call the lab');
await screen.getByRole('button', 'Add task').tap();
await expect(screen.getByRole('status', 'Open tasks')).toHaveText('2 open');

Agent steps: agent.act

You name the goal. The model looks at the screen and chooses the clicks. You still pin the outcome yourself, right after, with expect or agent.assert. That pin is what lets the next run replay the clicks without calling the model again.

await agent.act('add a task named {title}', { params: { title: 'Call the lab' } });
await expect(screen.getByRole('checkbox', 'Call the lab')).toBeVisible();

One goal per act. “Add the task” is one goal. “Mark it done” is the next. A goal that tries to do three things gives you one recording and no place to see which part broke.

On a real app. Use exact steps for money, counts, validation, and permissions. Use the agent for a long happy path whose buttons move around but whose outcome stays the same: an onboarding wizard, a booking flow, “get from the landing page to checkout”. The agent absorbs small copy changes. Your expect still guards the fact you care about.
The agent costs a model call the first time. npm run test:lab skips those tests. Sign in once with npx e2e login spacexai, then run npm run test:lab:agent. The model is grok('grok-4.7') in e2e.lab.config.ts. A passing run is saved under .e2e/cache/. The next run replays it. agent.assert and agent.extract always call the model. They are judgments, not recordings.

Tour of the tests

Run any single file by giving its path. Add --headed when you want to watch.

npx e2e run --config e2e.lab.config.ts lab/tests/patients.e2e.ts --headed

lab/tests/login.e2e.ts — the front door

Empty form, wrong password, a good sign-in, Enter in the password field, sign out, and a visit to /board while signed out. The good sign-in fills the password with credentials.user('receptionist').password. The test file never contains the password as a value it invented. The account lives in e2e.lab.config.ts. On a real project the password comes from the environment, and reports redact it.

On a real app. Every login, signup, and “session expired” redirect. Assert the error text and the URL you landed on. A test that only checks “some alert appeared” will stay green when you show the wrong error.

lab/tests/auth.setup.e2e.ts — sign in once

test.setup signs in and session.save('receptionist') stores cookies and local storage for this run. Any test with session: 'receptionist' starts already signed in. If you run only the board file, the setup still runs first.

On a real app. Admin, member, and billing-owner accounts. Sign each one in once, then write the tests about the feature, not about the login form. The login form keeps its own tests.

lab/tests/board.e2e.ts — create, filter, confirm

Adds a task and checks the count. Rejects an empty task. Submits with Enter. Marks a task done and uses the All / Open / Done tabs. Opens a delete dialog, keeps the task, then deletes it. Closes that dialog with Escape. Drives the browser’s own confirm() for “Clear finished”: dismiss leaves the task, accept removes it.

The count is a status with the accessible name “Open tasks” and the text 2 open. The test asks for that name, then checks the text. That is the pattern to copy: the name tells you which status, the text tells you the value.

On a real app. Carts, todo lists, review queues, “are you sure?” deletes, and old admin pages that still call window.confirm. Register browser.onDialog before the click that opens the native dialog.

lab/tests/patients.e2e.ts — tables, files, network

This file is the one to re-read when you test an admin screen.

  • Search as you type uses pressSequentially. Use that when the app reacts to each key. fill sets the whole value at once and is what you want for a normal form field.
  • Status filter and sort check the row headers in order. The order is the assertion. “The table has Maya in it” would still pass if the sort was backwards.
  • Export waits for the download and reads the file. The filter is Waiting, so the CSV contains Maya and Jonah and not Luis.
  • Refresh queue hits a real endpoint that takes a second. The test watches the progress bar, then the status text, and also reads the HTTP response.
  • Abort and stub replace that endpoint. One simulates a dead API. One returns a payload you chose, so the test proves the screen renders the response rather than a hardcoded sentence.
  • Tooltip is a hover. Visit slip is a dialog whose content lives in an iframe. Queries do not cross into an iframe. browser.frameLocator steps inside, and then the usual getByRole works.
On a real app. User tables, order tables, invoice export, “refresh” buttons, payment or search APIs you must not hit for real, embedded card forms, maps, and charts. Stub the network when the real service is slow, paid, or shared with other people. Assert the file contents when the product’s job is to produce a file.

lab/tests/intake.e2e.ts — a wizard

Step 1 refuses a missing or broken email. Step 2 refuses a missing reason or provider. Back keeps what you typed. The happy path uploads lab/fixtures/card.txt, checks the consent box, and expects the receipt “Saved intake for Maya Chen.”

On a real app. Checkout, onboarding, insurance, and any “step 2 of 4” form. Assert you stayed on the step when the input is bad. Assert the values survived Back. Assert the receipt, not only that the button was clickable.

lab/tests/settings.e2e.ts — state that must survive

Turns on email digests, leaves the page, comes back, and expects the switch to still be on. Turns on night theme, reloads, and expects both the words on screen and the night class on the page. The words are the contract a user sees. The class is extra proof the theme really changed.

On a real app. Settings, feature toggles, and anything saved in the browser or on the server. A switch that flips and flips back on refresh is a bug. Reload, or leave and return, before you call it saved.

lab/tests/shell.e2e.ts — layout and a dead link

Shrinks the window to a phone width before the page opens, then opens the menu and goes to Patients. The other test opens /not-a-page and follows “Back to the board”.

On a real app. The phone layout of a site you already test on desktop, and the 404 or empty state. Set the viewport before app.open when the first paint matters. A menu that only breaks at 390px wide will not show up in a 1280px test.

lab/tests/agent-board.e2e.ts — the model

Two goals, each followed by an exact check. The second test also asks the model to read the visible task titles into a Zod schema (agent.extract) and to judge one sentence (agent.assert). Judge the meaning. Do not assert the model’s exact paragraph.

On a real app. A journey you are tired of rewriting every time a label moves, as long as you still pin the outcome. Keep one act to one outcome. Put product vocabulary in agents.default.context in the config, the way this lab describes what “open tasks” means.

Finding things

Prefer the accessible name: the label, the button text, the heading. That is what a person using a keyboard or a screen reader uses, and it survives class-name refactors.

QueryUse it forExample in this app
getByRole(role, name)Buttons, links, headings, checkboxes, tabs, dialogs, status messagesgetByRole('button', 'Add task')
getByLabel(text)Inputs that have a <label>getByLabel('Email')
getByPlaceholder(text)An input whose only hint is the placeholderThe new-task field also has a label, so the label wins
getByText(text)A sentence on the pagegetByText('No tasks on this filter.')
getByRole(...).filter({ hasText })A row that contains some textNarrow a table row when the name is not on one cell
browser.frameLocator(css)Stepping into an iframeThe visit slip
browser.locator(css)A last resort, when nothing has a nameThe lab uses it once, for the html class

Names are exact. getByRole('button', 'Save') does not match “Save changes”. A locator that matches two things fails immediately. A locator that matches nothing waits, then fails. Fix the name. Do not add a sleep.

Actions you will reuse: tap, fill, pressSequentially, press('Enter'), check, selectOption({ label }), hover, setInputFiles.

On a real app. If a button has no accessible name, add one in the product (aria-label or visible text) instead of reaching for a CSS class. The test gets stable, and the product gets easier to use.

Checking things

expect on a locator retries for a few seconds. That is how you wait for a slow queue check. You do not write setTimeout.

CheckWhen
toBeVisible / toBeHiddenIt should be on screen, or gone
toHaveText / toContainTextThe words. toHaveText is the whole string. A list of strings checks order.
toHaveValue / toBeCheckedForm state
toHaveCountHow many matches. Zero is allowed: the thing is gone.
toHaveURL / toHaveTitleWhere you are. The URL is relative to the app.
expect(value).toBe / toContain / toMatchObjectA download, a JSON body, an agent.extract result. These do not retry.

A read such as textContent() answers once. If the number is still loading, use toHaveText so the runner keeps looking until it settles.

On a real app. --grep and a file path are how you rerun the one case you are fixing. --tag smoke is the two-minute check before you push. --last-failed is the loop after a red CI run. --headed is for the failure you cannot picture from the log. In CI you drop --headed, keep the same command, and upload .e2e-lab/report.json plus .e2e-lab/results.

When a test fails

  1. Read the error in the terminal. The code is a name such as LOCATOR_NOT_FOUND or ASSERTION_FAILED, plus the line in your test.
  2. Open the trace it prints, a trace.md under .e2e-lab/results/. It shows each step, the screen at the failure, and what the app logged.
  3. If the app log matters, open .e2e/logs/lab.log.
  4. Fix the locator, the expected text, or the app. Run that file again.

A locator that matches two nodes is LOCATOR_AMBIGUOUS. Make the name more specific. A check that never becomes true is ASSERTION_FAILED. The text on the screen and the text in the test disagree, or the screen never arrived.

Exit code 0 means the selected tests passed. Exit code 1 means a test failed. Exit code 2 means the command or the config is wrong, so retrying the same command will not help.

On a real app. The trace is the bug report. Screenshot, URL, and the step that failed are what you hand to the person who owns the page. Do not re-run ten times hoping it goes green. If it is flaky, the trace from the red attempt is the evidence.

Use it on a real app

Harbor Desk exists so the pieces are easy to see. A product you are testing already has its own URL. You point a config at that URL. You do not copy these screens.

import type { E2EConfig } from 'e2e';
import { web } from '@e2e-dev/web';

export default {
  targets: [
    {
      engine: web(),
      app: {
        url: 'http://127.0.0.1:3000',
        command: { executable: 'npm', args: ['run', 'dev'], log: '.e2e/logs/app.log' },
      },
    },
  ],
} satisfies E2EConfig;

That command starts the product, waits until the URL answers, and stops it when the run ends. For an app that is already deployed, skip command and set url to that site. That is what e2e.config.ts in this project already does.

Then write tests the way the lab does:

  • One file per area: login, the list, the wizard, settings.
  • A setup test for each account. Feature tests declare session.
  • Exact expect after every important step.
  • agent.act only for a goal, with {title} style params for values, and a check immediately after.
  • Network stubs for anything slow, paid, or shared.
  • A phone-sized viewport for the layout you know people use on a phone.
A useful first test on a product you already have. Sign in, open the main screen, and assert one heading and one URL. That single test tells you the runner can start, the account works, and the app booted. Grow from there one screen at a time. Tag it smoke and run it on every change.

Practice

Do these in order. Each one changes a test or adds one, then you run that file.

  1. Change the empty-task message in lab/public/app.js and update the matching line in lab/tests/board.e2e.ts. Run the board file. Put the message back if you want the suite green.
  2. Add a test that unchecks “Print the roster” and expects the open count to become 2 open.
  3. On Patients, filter to “Checked out” and export. Assert the CSV contains Priya Shah and does not contain Maya Chen.
  4. Run the board file with --headed and watch the delete dialog.
  5. Break a locator on purpose (ask for a button named “Save”). Run the file. Open the trace.md the terminal prints. Put the locator back.
  6. After npx e2e login spacexai, run npm run test:lab:agent twice. The second run should replay the recorded steps. npx e2e cache stats --config e2e.lab.config.ts shows the recordings.

The pages worth knowing by heart are Board and Patients. Between them they cover forms, lists, dialogs, tables, files, and a slow API. That is most of the UI testing you will do on a real product.
